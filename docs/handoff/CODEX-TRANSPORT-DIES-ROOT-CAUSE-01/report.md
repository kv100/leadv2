# CODEX-TRANSPORT-DIES-ROOT-CAUSE-01 — диагностика — 2026-09-06

Механизм **не доказан до конца**. Доказано другое: одна гипотеза опровергнута контрольной
группой, посылка самого брифа неверна, и выжила одна конкретная линия расследования с
адресом следующего замера. Правок поведения нет.

## 1. Опровергнуто: «брат уронил общий брокер»

Диагноз 2026-09-01 (SessionEnd одной codex-сессии рвёт брокер, которым пользуется другая)
проверен на данных, а не рассуждением. У каждого задания есть `startedAt`/`completedAt`, у
каждого ключа состояния — список заданий. Прямой тест: доля упавших заданий, внутри окна
которых завершился СОСЕД по тому же ключу.

```
группа                    n     сосед завершился в окне
transport_gone           73         5   6.8%
прочие именованные      212        12   5.7%     <- контрольная группа
без сообщения            75         2   2.7%
```

Обогащения нет: 6.8% против 5.7%. И решающее: **19 из 73 смертей `transport_gone`
произошли в ключах, где за всю историю было РОВНО ОДНО задание** — там некому было
ничего рвать. Гипотеза о брате как об общем механизме закрыта.

## 2. Посылка брифа неверна: брокеры изолированы не по заданию, а по РЕПОЗИТОРИЮ

Ключ состояния считается так (`lib/state.mjs:30-44`, `lib/workspace.mjs:3`):

```
workspaceRoot = ensureGitRepository(cwd)          # корень git, не cwd
key = basename(workspaceRoot) + "-" + sha256(realpath(workspaceRoot))[:16]
```

То есть 360 файлов `broker.json` — это 360 **корней git** (в основном рабочие деревья
линий, каждое — свой корень), а не 360 заданий. Внутри одного корня задания брокер
**делят**: `ensureBrokerSession` (`broker-lifecycle.mjs:114-116`) переиспользует запись,
если её endpoint отвечает. Это видно и на числах: у главного чекаута `leadv2` **102**
задания на один ключ, у `persona-engine` — **57**.

«Изолированы по своему временному cwd» — неверно: временный каталог свой у каждого ЗАПУСКА
брокера, а ключ общий на репозиторий. Но, как показывает §1, разделения мало.

## 3. Выжившая линия: сессионный TMPDIR уносит сокет живого брокера

`createBrokerSessionDir` кладёт каталог брокера в `os.tmpdir()`, и там же лежит unix-сокет.
Разбивка 360 записей по корню temp:

```
/var/folders/gr/…  (мой пользовательский temp)     224   каталога нет: 224
/var/folders/75/…  (ЧУЖОЙ контекст, мне не читаем) 122   «нет»: 122   <- НЕ ВЕРИТЬ, см. §4
/tmp/claude-503/cxc-*                               14   каталога нет: 14
```

`/tmp/claude-503/` — это **scratch-каталог сессии Claude Code**, который выставляется в
`TMPDIR` и уничтожается вместе с сессией. Брокер, порождённый изнутри такой сессии, кладёт
свой сокет туда. Когда сессия заканчивается, каталог сносится **вместе с сокетом живого
брокера**, а запись `broker.json` остаётся: teardown не выполнялся, иначе он удалил бы и
запись — `clearBrokerSession` идёт сразу за `teardownBrokerSession`. Следующее обращение к
этому брокеру и есть `transport_gone_app_server_absent`.

Согласуется со всем: записи переживают свои каталоги; `rmdirSync` в одиночку удалить их не
мог, потому что за ним всегда идёт очистка записи; наш слой к `cxc-*` не прикасается —
`grep -rn "cxc-"` по `plugins/leadv2` пуст.

**Чего не хватает для доказательства:** ни один каталог не наблюдался во время живого
задания. Нужен ровно один замер: пока codex-задание работает, следить за его `sessionDir`
и зафиксировать момент исчезновения вместе с тем, какая сессия в этот момент закончилась.
Репродьюсер для этого замера: `repro.sh` рядом с этим файлом (только чтение, ничего не
запускает сам).

## 4. Стальные 360 записей — симптом, и отчасти артефакт прибора

Не причина и не шум: это **отпечаток** случаев, где каталог исчез без teardown. Но считать
их поштучно нельзя, и вот честная граница: 122 записи лежат в `/var/folders/75/…`, корень
которого мне **не читается**. Мой `[ -d ]` отвечает «нет» и для отсутствующего каталога, и
для нечитаемого. Поэтому доказательным можно считать только `gr`-подмножество (224 из 224)
и `/tmp/claude-503` (14 из 14). Про 122 я не знаю ничего.

Живых pid среди записей два (май и июль). Это **не** живые брокеры: `kill -0` отвечает «да»
и на переиспользованный номер pid.

## 5. Правка ПОСТАВЛЕНА (решение соседа 2026-09-06, задача основателя «чтобы кодекс работал»)

Моя рекомендация была «не ставить до замера из §3». Она снята, и снята корректно: замер не
теряется, он меняет форму. Доля `transport_gone` уже измерена на 73 смертях — это база ДО,
и та же доля на том же счётчике через сутки есть замер ПОСЛЕ, причём на живом потоке, а не
на одном наблюдении. Не упадёт — гипотеза о сессионном TMPDIR опровергнута, и это результат
не хуже.

**База ДО, зафиксирована 2026-09-06** (пересчитывать теми же счётчиками):

```
transport_gone           73 из 360 отказов;  сосед завершился в окне  5/73  = 6.8%
прочие именованные      212;                                        12/212 = 5.7%
без сообщения            75;                                         2/75  = 2.7%
записей broker.json 360; из них с исчезнувшим каталогом 224 (gr) + 14 (/tmp/claude-503)
```

**Что сделано:** `codex-task.sh` пинит `TMPDIR` в собственный долгоживущий каталог плагина
(`~/.claude/plugins/data/codex-openai-codex/tmp`) вместо наследуемого сессионного, один раз
сразу после резолва companion — то есть на все четыре формы запуска сразу. Каталог не
реапится системой, поэтому там же ограниченная уборка: только `cxc-*` старше **семи** суток,
только в нашем каталоге. Более узкое окно воспроизвело бы ровно тот баг, который правится.

**Fail-open по построению:** если каталог не создаётся или не пишется, `TMPDIR` остаётся
ровно наследованным. Правка, которая ломает то, что защищает, хуже дефекта.

**Откат — одна строка:** убрать `export TMPDIR="${d}"` в `_codex_durable_tmpdir`, либо
выставить `LEADV2_CODEX_DURABLE_TMPDIR=0` без правки кода.

**Негативный контроль (требование строки):** каталог брокера, созданный под запиненным
корнем, **переживает снос сессионного scratch** — случай (b) сюиты
`test-codex-tmpdir-outlives-the-session.sh`. Чисто **5/0**; с мутацией (пин убран) **2/3**:
падают (a), (b) и (e), остаются зелёными (c) «непригодный каталог оставляет TMPDIR как был»
и (d) «уборка не трогает свежий брокер». Под мутацией (b) падает предметно — каталог брокера
исчезает вместе со scratch, то есть ровно исходный дефект.

`repro.sh` остаётся вооружённым: он ловит комбинацию «каталога нет, запись есть» независимо
от этой правки.

## 6. Что диагноз 2026-09-01 угадал, а что нет

**Верно:** смерть приходит извне задания, задание не виновато; запись брокера переживает
свой транспорт; teardown действительно убивает дерево процессов.
**Неверно:** «общий брокер» как причина — опровергнуто §1, включая 19 смертей там, где
делить было не с кем. Общность есть, но она по репозиторию, и сама по себе не убивает.
