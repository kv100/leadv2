# Unguarded source census -- DISPATCH-CLOSE-GATE-01

Generated by `test-lib-source-guarded.sh`'s `scan_unguarded()`: for every `.sh` under
`plugins/leadv2/scripts` and `plugins/leadv2/hooks`, any `source`/`.` of a `lib/`-path
sibling (anywhere), or -- in a file that already speaks `LEADV2_CANONICAL_ROOT` somewhere
(i.e. has opted into the symlink-safe idiom) -- any `source`/`.` of ANY sibling `.sh` file,
counts. "Guarded" means a local-or-canonical fallback in the loading block. Test files are
exempt from the broadened (non-`lib/`) check: a test always runs from a full checkout, never
as a standalone consumer symlink, so its own sourcing of the module under test is not a
deployment concern -- the plain `lib/`-path rule still applies to them.

Round 6 (DISPATCH-CLOSE-GATE-01) fixed TWO separate blind spots in the scanner itself, not
just the census:

1. The prior scan matched only a literal `/lib/` (or `.lib/`) substring in the sourced path,
   so it never inspected `leadv2-lane-child-suffixes.sh` or `leadv2-portable-lock.sh` -- both
   sourced by `leadv2-dispatch-code.sh` directly under `scripts/`, not `scripts/lib/`.
2. The line-match regex itself only matched a `source`/`.` statement that STARTS the line
   (`^\s*source ...`). The single-line idiom used at both of the sites above --
   `[[ -f "$X" ]] && source "$X"` -- never matched at all, guarded or not, because `source`
   there follows `&&`, not the start of the line. This meant the census was blind to that
   idiom everywhere, not just at those two sites; re-running the corrected regex surfaced
   five more previously-invisible in-lane instances of the exact same idiom, unguarded, in
   `leadv2-dispatch-code.sh` and `leadv2-dispatch-product-close.sh`, plus four more
   out-of-lane instances.

Both blind spots are fixed in `test-lib-source-guarded.sh` this round. All seven in-lane
sites the corrected scanner then found (2 from blind spot 1, 5 from blind spot 2) are fixed
in the production files below. Sites outside `LANE_WRITES` are left as documented gaps for a
future lane, per "Unguarded outside this lane's write set" below.
