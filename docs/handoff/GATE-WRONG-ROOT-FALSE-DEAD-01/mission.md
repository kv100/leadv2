# GATE-WRONG-ROOT-FALSE-DEAD-01 — e2e gate must run the lane's own suite from the lane's own root

Repo: ~/Projects/leadv2 (canonical plugin). Founder-approved 2026-08-03. FIVE false `dead/e2e_regression` verdicts in one day, all lanes whose own suites were green: M-8 (99f0fe0f, cluster-M), 3c663543, c0d41b9b, f0752b69 (mine — each later passed critic review + my own 25-28/28 suite runs and shipped to main). A gate that reliably buries green lanes is worse than no gate: every one of these required manual ledger surgery (backups .bak-falsedead-*) and would have permanently blocked re-dispatch via the write-once terminal + codex-lead dup-guard.

MECHANISM (evidence, docs/handoff/dispatch-3c663543/e2e-gate.log):
- leadv2-dispatch-product-close.sh resolves the e2e command via leadv2-e2e-entrypoint.sh "${ROOT}" → for this repo that is `<root>/tests/run-all.sh`, run with `--scope changed`.
- The failing log shows it executed the REPO-ROOT test family (`.claude/scripts/tests/run-core-offline.sh`, i.e. ~/Projects/leadv2/tests/run-all.sh's world — NOT the lane-modified plugins/leadv2/scripts/tests/run-core-offline.sh), and that suite self-reported `repo=/Users/kostiantyn.vlasenko/Projects` — the PARENT of all checkouts. 13 passed/8 failed, all failures foreign to the lane's diff.
- So two distinct wrongs: (W1) wrong suite family — the gate ran the repo-root harness while the lane's changes (and its new tests) live under plugins/leadv2/scripts/tests/; a lane's OWN new suite is never exercised and unrelated repo-root suites decide its fate. (W2) wrong root — some component resolved its repo root to ~/Projects (likely a `git rev-parse`/`cd` from an unexpected cwd, or run-all's own root discovery walking too far), which both breaks those suites and proves cwd/root is implicit, not pinned (the session-wide disease family).
