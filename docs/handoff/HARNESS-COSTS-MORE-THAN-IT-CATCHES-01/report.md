# HARNESS-COSTS-MORE-THAN-IT-CATCHES-01 — настоящие ли тесты

Вопрос основателя: тесты настоящие или мы платим за фикцию. Отвечаю числами, которые померила
сама, а не теми, что стоят в брифе.

## 1. Базовое число — и почему его до сих пор никто не видел

Прежде чем считать долю убитых мутаций, выяснилось, что **прибор не запускается вовсе**, и это
важнее самой доли.

### 1а. Он не запускается в общем дереве

`mutation-kill-rate.sh` выходит с кодом 1, если чекаут вызывающего грязен. На этой машине
persona-engine грязен ВСЕГДА — параллельные линии держат в нём свою работу:

```
cd ~/Projects/persona-engine && git status --porcelain | wc -l     # 17
```

То есть единственный замер, который заказал основатель, структурно недоступен любому, кто просто
запустит инструмент у себя. Я гоняла его в отдельном чистом рабочем дереве
(`git worktree add --detach`), и это обходной путь, а не решение.

### 1б. Каталог не проходит собственную валидацию

Первый же запуск умер на записи №12:

```
ValueError: catalog entry #12: missing required key 'patch' (id='arbiter-coerced-work-kind-is-not-named')
```

Валидация идёт по ВСЕМУ каталогу до фильтрации, поэтому одна испорченная запись обнуляет прогон
целиком — даже с `--only`. Обязательных ключей у раннера четыре (`id`, `file`, `anchor`, `patch`
— `scripts/mutation-kill-rate.sh:130`), и пяти записям не хватает `patch`:

```
#12 arbiter-coerced-work-kind-is-not-named        #17 arbiter-death-the-vocabulary-cannot-name-is-silent
#13 arbiter-partial-window-read-is-not-named      #18 arbiter-spawn-nobody-accounted-for-reads-as-clean
#14 arbiter-unconfigured-ceiling-is-not-named
```

**Поправка к себе, сделанная до отчёта.** Первый мой счёт объявил испорченными 15 записей,
потому что я включила в обязательные ключи `suite`. Раннер его не требует. Пересчитала по
ключам самого раннера: блокирующих пять, а не пятнадцать. Ошибка была в сторону обвинения
каталога — шестнадцатая такая за сутки, и правило прежнее: прибор врёт в сторону вывода, к
которому я склонна.

### 1в. Каталог двухрепозиторный, а раннер знает один

Это главное. В каталоге 39 записей, из них **29 помечены `repo: leadv2`**, а поле `repo` раннер
**не читает нигде**:

```
grep -nE '\brepo\b' scripts/mutation-kill-rate.sh    # только в комментариях
```

Пути он разрешает относительно чекаута вызывающего. Отсюда:

```
из чекаута persona-engine:  10 записей persona-engine — файл существует у 10
                            29 записей leadv2         — файл существует у 0
```

То есть **29 из 39 записей не могут быть посчитаны оттуда, где лежит каталог**, и дают
`anchor_missing` (код выхода 2, «гниль каталога»). Доктрина в `.claude/CLAUDE.md` — «kill rate
не может падать», «запись никогда не удаляется ради красивого числа» — отслеживает величину,
которую в таком виде нельзя вычислить ни из одного репозитория.

**И часть этого сделала я.** Сегодня я добавила в этот каталог записи с `repo: leadv2`, следуя
уже сложившемуся в нём соглашению — соглашению, которого раннер никогда не поддерживал. Пишу
это здесь, а не прячу: без этого признания находка выглядела бы как чужая небрежность.
