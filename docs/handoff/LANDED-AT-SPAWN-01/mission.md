# LANDED-AT-SPAWN-01 — spawn must never write terminal=landed; ledger keyed to dispatch target repo

Repo: ~/Projects/leadv2 (canonical plugin). Two live reproductions today (2026-08-03): tasks 9ae33035 (14:21:17Z) and 99324dc5 (15:47:40Z) each got a write-once `terminal=landed cause=spawned_glm` row AT SPAWN TIME, and both rows landed in the WRONG repo's ledger (`~/.claude/leadv2-state/persona-engine/dispatch-ledger.jsonl`) although task+worktree are leadv2. Both rows hand-purged (backups `dispatch-ledger.jsonl.bak-landedspawn`, `.bak-las2`).

MECHANISM (verified):
- `plugins/leadv2/scripts/leadv2-dispatch-code.sh:2513`: `[[ "${product_class}" != "product" ]] && _dl_note "${sig8}" landed "spawned_${candidate}" ...` — for a non-product classification the spawn path itself writes the write-once TERMINAL row while the async worker (glm/kimi/codex/sonnet bg) has done zero work. The guarding comment assumes non-product spawns are fire-and-forget; that assumption is false for every async arm: the worker can die, and "landed" is a lie that (a) permanently blocks the lane's real terminal under write-once semantics, (b) makes leadv2-codex-lead.sh dup-guard refuse the task as already done.
- Repo keying: `leadv2-dispatch-ledger.sh` resolves the ledger path via `PROJECT_ROOT` (repo_slug/state-path resolver). dispatch-code.sh inherits PROJECT_ROOT/CLAUDE_PROJECT_DIR from the CALLER SESSION env, so a dispatch launched from a persona-engine session into a leadv2 lane writes leadv2 terminals into persona-engine's ledger.

REQUIREMENTS:
1. NO TERMINAL AT SPAWN: remove/replace the `:2513` landed-write. A non-product spawn writes a RESERVATION/progress row at most (the reservation machinery exists — reserve/confirm paths in leadv2-dispatch-ledger.sh), never `terminal=landed`. If a non-product arm is truly synchronous-and-completed inside dispatch-code (worker ran to completion before this line), landing is legitimate — gate the write on evidence of completion (e.g. sync arm rc==0 with the worker finished), not on classification alone. If no such sync path exists, the write is simply removed; absence-of-terminal is the honest state.
2. LEDGER REPO-KEYING BY DISPATCH TARGET: every `_dl_note` / LEDGER_BIN invocation from dispatch-code.sh must key the ledger to the DISPATCH TARGET repo — the main checkout that owns the lane worktree (derive from WORK_ROOT / lane worktree's `git rev-parse --git-common-dir`, or the --repo/-C target the dispatch resolved), NOT the caller session's env. Thread it explicitly (e.g. `PROJECT_ROOT=<target>` on the LEDGER_BIN call or a dedicated env the ledger honors) so the same fix covers reserve/confirm/terminal writes uniformly. Do not change leadv2-state-path.sh semantics for other callers.
3. AUDIT SIBLING WRITES: grep dispatch-code.sh for every other `_dl_note`/ledger write on the spawn path (refused/parked at pre-spawn are fine — those ARE terminal facts) and confirm each writes a fact that is true AT THE MOMENT of writing. Fix any other spawn-time future-claims found. List them in the report either way.
4. NON-GOALS: no changes to write-once semantics themselves, no product-close changes (GLM-DIED-WITH-WORK-RESUME-01 is a separate queued task), no schema changes to ledger rows beyond what reservation rows already support, no supervisor/fanout changes.
