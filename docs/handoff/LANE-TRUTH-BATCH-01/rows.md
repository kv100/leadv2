## LANE-REGISTRATION-ONLY-ON-FANOUT-PATH-01 (id f8e2da0c065a)
LANE-REGISTRATION-ONLY-ON-FANOUT-PATH-01 (P1): a lane launched directly via leadv2-dispatch-code.sh is invisible to every supervisor surface. Evidence 2026-07-30 17:07: lane dispatch-8e5b4e0e was launched with leadv2-dispatch-code.sh (deliberately bypassing fanout, which was killing its own lanes per P0-FANOUT-EXIT-KILLS-ITS-OWN-LANES-01). The lane is genuinely alive — architect prepass pid 47135, architect.stream.jsonl 242KB and still growing — but grep 8e5b4e0e docs/leadv2/active.yaml returns 0 hits, and the status line (leadv2-lane-status-line.sh, which counts lanes from active.yaml) shows 'lanes 0/5'. Root cause: active.yaml registration is written by leadv2-fanout.sh, not by the launcher that actually starts the worker, so any launch path other than fanout produces an unregistered lane. Consequence: the status line under-reports, the supervise loop cannot see the lane, and the T-o terminal-state ledger has no row to close. Fix by moving registration to the launcher (leadv2-dispatch-code.sh) so registration is a property of launching a worker, not of which caller launched it. Related but distinct from LANE-LIVENESS-BLIND-TO-FUNNEL-PATH-01, which is about the liveness reader probing docs/handoff/<task-id>/ instead of docs/handoff/dispatch-<hash>/.
