## 1. Что решено

**Решения нет.** Ни один из трёх проектов не выстоял: два опровергнуты тем, что чинят
несуществующий дефект (механизм уже закрыт в другом месте), третий — тем, что подключается
перед матрицей и сносит работающую сегодня safety-гарантию. Выдать любой из них за решение
значило бы поставить правку туда, где уязвимости нет, и снять защиту там, где она есть.

Вместо решения — измеренная база, на которой следующий раунд обязан стоять. Каждый пункт
получен прогоном, команда приложена.

Общий стенд проб (стаб квоты обязателен, `bash -c`, не zsh — в zsh нет BASH_SOURCE и
библиотека ложно проваливается):

```bash
# /tmp/q.sh — стаб квоты, форма выведена чтением util() (route-arbiter.sh:189-235)
# {"glm":{"status":"ok","five_hour":{"pct":10},"weekly":{"pct":10}},
#  "codex":{"status":"ok","windows":[{"kind":"five_hour","used_percent":10}]},
#  "anthropic":{"status":"ok","accounts":[{"active":true,"status":"ok",
#    "account_label":"a","five_hour":{"pct":10},"seven_day":{"pct":10}}]}}
cd ~/Projects/leadv2 && bash -c '
 source plugins/leadv2/scripts/lib/leadv2-route-arbiter.sh
 export LEADV2_QUOTA_LIVE=/tmp/q.sh
 route_arbiter worker "{\"kind\":\"code\",\"size\":\"standard\",\"allowed_arms\":[\"sonnet\"]}"'
```

Ловушка, в которую я попал первым прогоном и которую следующий раунд обязан обойти: со стабом
квоты **неверной формы** каждый арм отвечает `rc=3 arm=refuse`, и проба выглядит как «всё
сломано». Ноль здесь — сломанный запрос, а не факт о мире.

### F1. Круговая зависимость РЕАЛЬНА — но только вне protected. Измерено.

Два дескриптора, идентичные по всем полям задачи, различающиеся только тем, какой арм
допущен, дают **разный** эффорт:

```
{"kind":"code","size":"standard","allowed_arms":["glm-flash"]}  => arm=glm-flash effort=low
{"kind":"code","size":"standard","allowed_arms":["sonnet"]}     => arm=sonnet    effort=medium
```

Механизм: `plugins/leadv2/scripts/lib/leadv2-route-arbiter.sh:409-419` — `_effort_row_matches`
сверяет `set(row['tags']) & set(w.get('tags'))`, где `w` — победитель ценового аукциона
(та же функция, строка ~403 `w=alternatives[0] if alternatives else ok[0]`). Теги — это
самоописание АРМА (`config/leadv2-routing.yaml:99-114`), не задачи. Это единственный
подтверждённый дефект темы.

### F2. Для protected / safety / ui_judgment циркулярности НЕТ. Измерено.

```
{"kind":"code","size":"standard","protected":true} => arm=glm effort=high
{"kind":"code","size":"standard","safety":true}    => arm=glm effort=high
```

Две независимые защиты, обе прочитаны построчно:
- admission-фильтр `leadv2-route-arbiter.sh:312` — `(not require_trusted or c.get('protected',False))`:
  арм с `protected: false` (glm-flash) физически не попадает в `ok`, т.е. не может стать `w`;
- ряд `{protected: true, effort: high}` (`config/leadv2-routing.yaml:131`) сверяется с
  **route-level** переменной `protected` (`route-arbiter.sh:414` против `:108-110`
  `protected=_prot_flag or _hard_flag`), а не с полем ячейки. `w.get('protected')` в файле
  не встречается ни разу.

Проект «от цены ошибки» бил в эту уже закрытую дверь.

### F3. Для Anthropic-армов поверхность эффорта мертва на три четверти.

| арм | доходит ли эффорт | file:line | что измерено |
|---|---|---|---|
| sonnet | **да, единственный** | dispatch-code.sh:5805-5809 → claude-subsession.sh:70,571 → `claude --effort` | сегодня достижимы ровно {medium, high}: теги sonnet `[integration, ui_judgment]` не матчат ни один low-ряд; `kind=plan` / protected / safety дают high |
| haiku | нет | lib/leadv2-glm-policy-resolve.py:55 `DISPATCHABLE_BUILD_ARMS={glm,glm-flash,codex,sonnet,freepool}` | ветки `haiku)` в spawn_worker нет вообще (grep пуст). Арбитр выдаёт `effort=low` на recon/audit — величина никуда не идёт |
| opus | нет | cmd_resolve (dispatch-code.sh:7033) выходит `exit 3` в опус-ветке ~7870; единственный `route_arbiter` этой функции — на 7970 | опус не доходит до арбитра; RESOLVED_EFFORT остаётся дефолтом `medium` со строки 7828, а printf route_resolved (7863) не печатает `effort=` вовсе |
| sonnet-как-ревьюер | нет | leadv2-dispatch-product-close.sh:482 вызывает `route_arbiter reviewer`, но `effort=` из вывода не парсит | grep «effort» по файлу даёт только «best-effort» в комментариях |

### F4. Словарь: расхождение есть, но обратное заявленному.

`claude --help` (CC 2.1.260) — `--effort <level>` принимает **(low, medium, high, xhigh, max)**.
Матрица эмитит только {low, medium, high} (`routing.yaml:127-136`). Строка usage
`claude-subsession.sh:56` говорит `[--effort <max|high>]` — это устаревший ТЕКСТ, а не
валидация: строка 70 присваивает значение без проверки, 571 передаёт как есть. Значит
«блокирующий разнобой словарей» не блокирует ничего; настоящий разрыв — что `xhigh`/`max`
(«ultra» из имени задачи) матрица не умеет выдавать вовсе.

### F5. `changed_files` арбитр не читает.

grep пуст; измерено: `{"kind":"code","changed_files":["agent/safety/pre-execute.sh"]}` →
`arm=glm-flash effort=low`. Реальная деривация protected живёт выше по потоку:
`dispatch-code.sh:7006 _lane_writes_class`, `:7711 _effective_protected`, `:7955-7960`
(скан миссии на `safety_gate|publish|payments` + ui-ключевые слова) → `_arb_protected`.

## 2. Расхождения проектов и как каждое разрешено

**D1. Есть ли круговая зависимость вообще?** П1 — «да, структурно»; П2 — «да, и она опасна
на safety»; скептики П2 — «нет, admission-фильтр закрывает». *Разрешение: расщепить по
protected.* Оба лагеря правы о своей половине: вне protected она измерена (F1), внутри
protected её нет (F2). Спрятать это выбором одного проекта — потерять половину анализа.

**D2. Куда переносить резолвинг — на поля дескриптора (П1) или на task-risk из путей (П2)?**
*Разрешение: ни туда, ни туда в предложенной форме.* П1 теряет информацию (после удаления
`tags` механическая и состязательная работа одного `kind` падают в один default-ряд —
именно та дифференциация, ради которой матрица существует). П2 дублирует то, что upstream
уже делает (F5). Правильная форма — не «убрать теги», а «взять теги ЗАДАЧИ вместо тегов
арма»; таких полей в дескрипторе сегодня нет, их надо завести (см. U1).

**D3. Статика или обучение (П3)?** *Разрешение: обучение сейчас нельзя.* Бандит по ключу
`(kind,arm)` ставится ПЕРЕД матрицей и не несёт protected — история, накопленная на
незащищённых задачах, начнёт выдавать low/medium там, где сегодня безусловно high, т.е.
сносит F2. Если бандит когда-либо, то только ВНУТРИ ряда `default` (после того как high-ряды
отработали) и с ключом, включающим protected.

**D4. Опус: передавать `--effort` (П1) или писать в reservation-запись (П2)?**
*Разрешение: обе правки преждевременны* — опус не спавнится вовсе (F3), передавать некуда.
Осмысленная правка ровно одна и дешёвая: печатать `effort=` в route_resolved (строка 7863),
чтобы присвоенный риск-уровень был наблюдаем при ручном вызове.

**D5. Haiku: включить в DISPATCHABLE_BUILD_ARMS (П1) или удалить лживый комментарий (П2)?**
*Разрешение: это вопрос допуска арма, а не эффорта.* Пока `haiku)` нет даже в spawn_worker,
его `effort=low` — мёртвая величина. Не смешивать с этой темой.

**D6. Словарь эффорта.** П3 назвал `{max,high}` vs `{low,medium,high}` блокирующим.
*Разрешение: снято измерением (F4)* — валидации нет, строка usage просто устарела.

## 3. Негативные контроли: мутация → что краснеет

**Почему все три заявленных контроля не годятся** (это не придирка, это причина, по которой
проекты опровергнуты):

- **П1.** Мутация возвращает чтение `w.get('tags')` в функцию, которую сам проект переносит
  ТУДА, ГДЕ `w` ЕЩЁ НЕ ПРИСВОЕНА. Оба прогона падают одинаковым `NameError` до выбора арма,
  assert на идентичность эффорта проходит — ложный зелёный, а не заявленное расхождение.
- **П2.** Мутация `!= protected` → `!= bool(w.get('protected'))` прогнана на scratch-копии:
  результат до и после **идентичен** (`effort=high` в обоих), потому что admission-фильтр
  (:312) гарантирует `w['protected']==True` всякий раз, когда `require_trusted`. Не краснеет.
- **П3.** Мутация `max→min` вносится в функцию, которой не существует; про сегодняшний путь
  контроль не доказывает ничего.

**Контроль, который засчитается — для F1, единственного подтверждённого дефекта.**
Сначала ПОЗИТИВНЫЙ контроль (доказать, что инструмент умеет отличать): пара дескрипторов,
идентичных во всём кроме `allowed_arms`, СЕГОДНЯ даёт `low` vs `medium` — это измерено выше
и это ненулевой ответ из того же источника. Assert будущего фикса: пара обязана давать одно
и то же значение. Негативный контроль после фикса — вернуть в тело `_effort_row_matches`
строку

```
if not (set(row.get('tags') or []) & set(w.get('tags') or [])): return False
```

(то есть сегодняшнюю форму), мутацию вносить **якорем по regexp внутрь тела функции**, не по
номеру строки — вставка на верхнем уровне покраснит все сюиты по неверной причине и прочтётся
как проход. Красное здесь — расхождение `low` vs `medium`, наблюдаемое в stdout, а не
одинаковая трассировка краха: именно это отличает контроль от П1.

**Второй обязательный контроль — «эффорт доезжает до CLI».** Держать реальным спавн-кейс
sonnet в `leadv2-dispatch-code.sh:5788-5809`, подделывать уровнем НИЖЕ: подменить
`claude-subsession.sh` эхо-скриптом, печатающим argv. Мутация — удалить строку 5806
(`[[ -n "${RESOLVED_EFFORT:-}" ]] && _sonnet_effort_args=(--effort ...)`); в эхо пропадает
`--effort`, сюита краснеет. Тест, который стабит сам `spawn_worker`, не доказывает ничего —
это ровно та форма, что держала харнесс зелёным сквозь три реальные поломки.

CI обязан ВЫБИРАТЬ обе сюиты: без строки в `EXTRA_SUITE_MAP` зелёный тест не стоит ничего.
Полный `tests/run-all.sh` не запускать — только
`LEADV2_RUN_ALL_SELECT_ONLY=1 bash tests/run-all.sh --scope changed`.

## 4. Чего мы НЕ знаем (UNVERIFIED) и чем проверяется

- **U1. Есть ли у задачи признак «механическая против состязательной» ДО выбора арма.**
  `DC_COMPLEXITY`/`DC_DURATION_CLASS` едут в дескриптор (dispatch-code.sh:7968), но их живое
  распределение не мерено. Если большинство — `unknown`, любая матрица по ним схлопывается в
  `default`, и «перенос на свойства задачи» даёт константный medium — та же болезнь, только
  на шаг раньше. *Проверяется:* подсчёт `complexity=`/`duration_class=` по decision-журналам
  за 7 дней. **Я это не мерил.**
- **U2. Как часто живые спавны вообще уходят на Anthropic-армы.** Если sonnet выигрывает
  редко, вся тема низкоприоритетна. *Проверяется:* подсчёт `route_resolved ... arm=sonnet`
  в decision-журналах за 7 дней.
- **U3. Меняет ли `--effort` измеримый исход.** Ни одного измерения: медиана токенов, время,
  доля fix-round при medium против high на sonnet. Без этого любой выбор эффорта — вера.
  *Проверяется:* A/B на одном классе задач.
- **U4. Нужны ли `xhigh`/`max` («ultra» из имени задачи) и на каком классе.** CLI их принимает
  (F4), матрица не выдаёт. *Проверяется:* чтением `docs/model-effort-matrix.md` — доктринальный
  документ я в этом проходе не открывал.
- **U5. Есть ли потребители `RESOLVED_EFFORT` вне dispatch-code.sh/claude-subsession.sh.**
  *Проверяется:* `grep -rn RESOLVED_EFFORT plugins/leadv2/scripts/`. Я грепал только эти два.
- **U6. Что `claude --effort low` физически делает на sonnet.** `--help` даёт список значений,
  не семантику. *Проверяется:* пробным прогоном с замером токенов/латентности.

## 5. Первый шаг — что делает первая линия работы

**Первая линия — не правка, а аудит на три числа.** Читает decision-журналы, ничего не меняет:

- **(a)** распределение `DC_COMPLEXITY` / `DC_DURATION_CLASS` среди живых `route_resolved` (U1);
- **(b)** доля спавнов на sonnet / haiku / opus за 7 дней (U2);
- **(c)** есть ли хоть одна живая строка `effort_applied ... arm=sonnet` — сегодня она не
  эмитится вовсе (единственный `effort_applied` в файле — GLM, dispatch-code.sh:5626), так что
  ответ известен заранее: ноль, и это ноль по построению, а не сломанный запрос.

Эти три числа и решают, что строить дальше:
- если (a) в основном `unknown` — чинится классификатор, а не матрица эффорта;
- если (b) около нуля — тема закрывается как низкоприоритетная, без единой правки;
- (c) уже даёт первую и единственную безусловную правку кода: одна строка
  `emit decision "effort_applied ... arm=sonnet effort=${RESOLVED_EFFORT}"` рядом с 5805 плюс
  `effort=` в опус-printf (7863) — чтобы у следующего раунда было что мерить.

Порядок после аудита, если он говорит «строить»: **1)** наблюдаемость (обе строки выше);
**2)** позитивный контроль F1, зафиксированный как тест, который CI выбирает; **3)** и только
потом — форма резолвинга, и не раньше, чем U1 ответит, есть ли у задачи признак, на который
её вообще можно перенести.
