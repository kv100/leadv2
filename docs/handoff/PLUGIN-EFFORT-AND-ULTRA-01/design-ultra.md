# Встраивание многоагентной проверки (ultracode/ultrareview) в фазы плагина

Статус: **РЕШЕНИЯ НЕТ.** Второй заход по теме — снова ни один из трёх проектов не
выстоял, и снова по той же причине (условие включения не доходит до входа движка).
Рецидив на одном и том же дефекте — сам по себе результат: тема не «куда встроить
многоагентную проверку», а «почему любое условие включения в этих движках мертво».

Ниже — не замаскированный выбор одного из проектов, а установленная пробами почва +
список того, что нужно выяснить, чтобы решение стало возможным.

Все проверки — чтение и пробы в `~/Projects/leadv2`, чекаут не менялся, ничего не
коммитилось. Bash-библиотеки пробовались под `bash -c`. Каждый ноль ниже сопровождён
ненулевым контролем из того же источника.

---

## 1. Что решено

**Механизм не выбран. Выбирать не из чего:** два проекта опирались на сигнал, которого
в точке врезки не существует; третий переизобретал уже работающий механизм и врезался
до объявления собственных входов. Решено следующее — это факты почвы, каждый с командой.

### 1.1. «ultracode» и «ultrareview» — два разных объекта, а не один инструмент

| Что | Что это на самом деле | Проверка |
|---|---|---|
| `ultracode` | **Не CLI-команда.** В этом репозитории это действующая текстовая инструкция лида ULTRACODE-FOR-HEAVY-01 — `plugins/leadv2/commands/leadv2.md:142`: при классе Heavy/Strategic лид SHOULD оркестрировать тяжёлые фазы как ad-hoc `Workflow`-скрипты (adversarial verify panels, loop-until-dry finders, judge panels). Кода нет, гейта нет, телеметрии исполнения нет. | Полный листинг `claude --help` (секция `Commands:`) не содержит `ultracode`; ненулевой контроль: тот же листинг даёт 13+ команд, включая `ultrareview`. `grep -rn -i ultracode plugins/leadv2/` → ровно 1 совпадение, и это `commands/leadv2.md:142` |
| `ultrareview` | **Реальная подкоманда CLI.** `claude ultrareview [options] [target]` — «cloud-hosted multi-agent code review of the current branch (or a PR number / base branch)». Опции: `--json`, `--timeout <minutes>` (**default 45**), `--post`/`--no-post` (no-post по умолчанию). | `claude ultrareview --help` |

Следствие: половина темы («ultracode») уже «внедрена» — как инструкция без исполнителя;
вопрос по ней не «куда встроить», а «срабатывает ли она вообще и чем это измеряется».
Вторая половина («ultrareview») — внешний облачный вызов с 45-минутным дефолтом. Все три
проекта писали «ultracode/ultrareview» как один инструмент — ошибка на входе,
унаследованная всеми тремя.

### 1.2. Единая причина падения всех трёх проектов: сигнал эскалации не доходит до движка

| Движок | Класс задачи | Признак риска (пути) |
|---|---|---|
| `leadv2-review-run.sh` | **НЕТ.** Аргументы только `--task/--root/--handoff/--diff/--author/--fanout/--task-dir` (блок arg-parse, L66-84). `grep -cE 'task_class|TASK_CLASS|--class'` → **0**; ненулевой контроль из того же файла: `grep -cE 'TASK'` → **66** | **ЕСТЬ**, но см. §1.4 |
| `leadv2-plan-run.sh` | Парсится (`--class`, L58) и **не используется**: `grep -n TASK_CLASS` → только L46 (инициализация) и L58 (парсинг). Боевой вызов `plugins/leadv2/docs/phases.md:151-155` `--class` не передаёт; других не-тестовых вызовов в дереве нет | НЕТ |
| `leadv2-llm-judge.sh` | **ЕСТЬ** (L47 default `Standard`, L52 `--class`) | **НЕТ** — `can_skip` (L325) = `is_light and offlimits_clean and premortem_proceed and hack_block`, ни одного path-терма |

Ровно поэтому проект №1 (гейт по `task_class` внутри review-run) и проект №2 (панель
архитекторов по `task_class` внутри plan-run) опровергнуты одним способом: **их условие
активации никогда не станет истинным**, и оба уходят в мёртвый код.

Отдельно по проекту №3: его enforcement-точка (`llm-judge.sh:325`) на своём же целевом
сценарии недостижима. `leadv2-llm-judge.sh:103-121` — dual-path: при `TASK_CLASS` из
{Light,Standard} и исполняемом `leadv2-llm-judge-haiku.sh` сначала зовётся Haiku, и при
вердикте go/no_go скрипт делает `cp` + **`exit 0` (L118)** — до сборки пакета, внутри
которой живёт L325. Вердикт Haiku считается только из premortem и hack-находок
(`leadv2-llm-judge-haiku.sh`), path-риск там не читается. То есть «Light-задача трогает
`agent/safety/*` при чистых premortem/hack» — именно тот случай, который проект №3
собирался закрыть, — выходит из скрипта, не дойдя до правки.

### 1.3. Риск-по-путям уже реализован и уже подключён в review-run

`plugins/leadv2/scripts/lib/leadv2-review-signals.sh` → функция `leadv2_review_signals`:
матчит тронутые пути против `protected_path_patterns` из per-repo routing yaml с fallback
на канонический, возвращает `{"protected_path","safety_touched"}`, fail-closed на всех
деградациях (`no_lane_writes_failclosed`, `no_patterns_failclosed`,
`lib_missing_failclosed` → `true/true`).

Подключение в `leadv2-review-run.sh`: source L146-152, вызовы L153 и L1125, гейт
`_engine_security_pass_enabled()` (L1117+) → `SECURITY_REVIEW_ENABLED` (L1382-1386),
который включает security-проход (L1474) и разрешает верификатор-политику
(`_engine_verifier_policy_enabled`, L1152).

Поэтому проект №3 («новый `leadv2-risk-gate.sh` в review-run») опровергнут дважды: он
добавлял третью параллельную реализацию path→risk (первые две — `leadv2_review_signals`
и `_lane_writes_class` в `leadv2-dispatch-code.sh:7001`) на тот же choke-point, и врезал
её «после блока `_REVIEW_LOCK_SH` (L58-64)» — то есть **до** объявления `DIFF_FILE`/`ROOT`
(они появляются в блоке «1. Arg parsing», L66+), так что классификатор получал бы пустой
diff на каждом вызове и по собственному fail-closed правилу всегда отвечал бы `risky`.

### 1.4. Существующий risk-сигнал дискриминирует только на dispatch-лейне; на лид-пути он всегда «риск»

- `leadv2-review-run.sh:109` — `WRITES_CSV="${LEADV2_DISPATCH_LANE_WRITES:-}"`, другого
  источника нет (собственного `--writes` у скрипта нет).
- Переменную экспортирует ровно один продовый писатель: `leadv2-dispatch-code.sh:5369`
  (`LEADV2_DISPATCH_LANE_WRITES="${lane_writes_csv}"`), она наследуется в
  `leadv2-dispatch-product-close.sh`, который зовёт движок на L2957 — **это ненулевой
  случай**, доказывающий, что источник умеет отвечать не-пустым.
- Лид/интерактивный вызов (`phases.md:276-280`) переменную не ставит →
  `no_lane_writes_failclosed` → `protected=true, safety_touched=true` →
  `SECURITY_REVIEW_ENABLED=1` **на любом diff, включая docs-only**.

Всегда-истинный fail-closed сигнал — не классификатор риска. На лид-пути сегодня нет
разницы между правкой `agent/safety/pre-execute.sh` и правкой README, и любая схема
эскалации «по признаку риска» на этом пути начнёт со 100% срабатывания.

### 1.5. Верификатор, который проект №1 собирался расширять, существует — и он синхронный, без таймаута

`leadv2-review-run.sh:1769-1799`: для каждой Critical/High находки выбирается
`_verifier_arm != _arm` из `ran_arms`, вызывается `_engine_verify_job` (объявлен L1157),
вердикт upheld/refuted/unverified пишется в поле `verifier_verdict` JSON-строки находки.
Условие входа — `REVIEW_FINDINGS_DISPUTED` (L1655-1657, считается по union-вердикту)
**И** `_engine_verifier_policy_enabled` (= `SECURITY_REVIEW_ENABLED`, L1152).

Новое, чего не было ни в одном из трёх проектов и ни в одном опровержении:
**`_engine_verify_job` вызывается синхронно внутри `while`-цикла (L1783) и ничем не
ограничен по времени.** Единственный bounded-wait wrapper — `_engine_run_arm_with_timeout`
(L1101, `ARM_TIMEOUT_S="${LEADV2_REVIEW_ARM_TIMEOUT_S:-900}"`), и он вызывается ровно в
одном месте — L1472, фан-аут ревьюер-арм. `grep -n '_engine_run_arm_with_timeout'` даёт
две строки: объявление (1101) и вызов (1472). Верификатор им не обёрнут.

### 1.6. Числовой конфликт: ultrareview не помещается ни в одну из двух точек врезки

Это уже не «риск», а арифметика по двум измеренным числам:

- **Как арм** (L1472, единственная точка с watcher'ом): watcher убивает job через
  `ARM_TIMEOUT_S=900` (15 мин). Дефолтный таймаут `claude ultrareview` — **45 мин**.
  Облачный ревью будет убит на трети срока, и результат превратится в пустой/частичный
  вывод, который движок обязан трактовать как `unverified`.
- **Как верификатор** (L1783, точка, которую называл проект №1): watcher'а нет вообще, а
  цикл последовательный — по одному вызову на каждую Critical/High находку. N находок ×
  до 45 мин блокирующего облачного ожидания, внутри round-cap-контракта фазы 5.

Поэтому вариант П1 («обернём тем же timeout-watcher, что уже используется для арм») не
существует как описан: в точке верификатора этого watcher'а нет, а в точке арма его
таймаут втрое меньше дефолта инструмента.

| # | Расхождение | Разрешение (одна фраза) |
|---|---|---|
| A | Куда врезаться: фаза 5 (П1) / фаза 2 (П2) / отдельный риск-гейт вне фаз (П3) | Расхождение мнимое — все трое упираются в один дефект (§1.2), поэтому вопрос «куда» преждевременен, пока условие включения не доходит ни в одну из трёх точек. |
| B | Новый классификатор риска (П3) vs переиспользование существующего | В пользу переиспользования `leadv2_review_signals`: третья реализация path→risk дала бы два несогласованных fail-closed вердикта на одном choke-point — но переиспользовать нечего, пока его вход на лид-пути пуст (§1.4). |

| D | `ultrareview` как tie-break-судья при расхождении верификаторов (П1) vs как третье обязательное условие `status: pass` (П3) | Ни то ни другое, и уже не по «неизвестности»: обе точки врезки измерены и обе не держат 45-минутный синхронный вызов (§1.6) — ultrareview может быть только асинхронным этапом вне round-контракта фазы 5, а такого этапа в плагине сегодня нет. |
| E | Панель независимых архитекторов (П2) vs критик одного черновика (сегодня) | Угол П2 — единственный, не дублирующий существующий механизм (`fanout_list` строится размером `PLAN_FANOUT`, а используется только элемент 0); сохраняем как кандидата, но механизм активации переписывается целиком, потому что заявленный (`--class`) мёртв. |
| F | Формат негативного контроля | Полное согласие всех трёх: мутация вносится regexp-якорем по уникальной строке **внутри тела функции**, никогда по номеру строки — самая надёжная часть анализа, закрепляем как обязательный формат (§3). |
| G | «Многоагентность» = внешний ultracode-инструмент (П1, П3) vs собственный фан-аут плагина (П2) | В пользу П2 по факту: `ultracode` инструментом не является (§1.1), поэтому многоагентность внутри фаз 2 и 5 может быть только собственным фан-аутом плагина; `ultrareview` — отдельный внешний кросс-чек, а не источник многоагентности внутри фазы. |
| H | Где enforcement для «риск ⇒ вторая пара глаз обязательна»: review-run (П1/П3) vs `llm-judge.sh:325` (П3) | Ни там, ни там как заявлено: llm-judge на целевом сценарии выходит раньше через dual-path Haiku (§1.2), а review-run уже имеет свой risk-гейт, вход которого слеп на лид-пути (§1.4) — точку выбирать заново, после Ш3. |

## 3. Негативные контроли: мутация → что краснеет

Контроль для несуществующего механизма построить нельзя — все три проекта строили
контроль для кода, которого нет (`_engine_ultra_verify_job`, `run_panel_architects`,
`leadv2-risk-gate.sh`). Поэтому здесь — контроли для фактов §1, которые обязаны быть
закреплены **до** любого проектирования. Первые три — falsifying-тесты: они красные на
текущем коде, и это и есть доказательство дефекта.

**К1 — риск-сигнал на лид-пути слеп.**
Тест: вызвать `leadv2-review-run.sh` БЕЗ `LEADV2_DISPATCH_LANE_WRITES` на docs-only diff,
assert `review_security task=… enabled=0` в журнале (эмит L1386). Сегодня: `enabled=1` →
**красный**. Реальная функция под проверкой — `_engine_security_pass_enabled` целиком;
подделывается на уровень ниже только routing yaml (фикстура с `protected_path_patterns`),
ровно как это уже делает `plugins/leadv2/scripts/tests/test-review-engine-v3-core.sh`.
Парный ненулевой контроль обязателен: тот же тест с
`LEADV2_DISPATCH_LANE_WRITES=secure/policy.sh` обязан дать `enabled=1`.

**К2 — класс задачи не доходит до plan-run.**
Тест: выполнить командную строку из `phases.md:151-155` дословно и assert, что движок
видит непустой `TASK_CLASS`. Сегодня: пусто → **красный**.

**К3 — enforcement llm-judge недостижим на своём целевом сценарии.**
Тест: `leadv2-llm-judge.sh --task-id T --class Light` с исполняемым
`leadv2-llm-judge-haiku.sh`-стабом, возвращающим `verdict: go`, и фикстурой, где
premortem/hack чисты. Assert: выполнение доходит до сборки пакета (маркер в логе).
Сегодня не доходит (`exit 0` на L118) → **красный**. Это тест, которого не было у П3:
его собственный контроль стартовал уже ниже точки выхода.

**К4 — ultrareview не помещается в фазу 5 (§1.6).**
Проверка-арифметика, не прогон: assert, что дефолт `ARM_TIMEOUT_S` (900 с) меньше дефолта
`claude ultrareview --timeout` (45 мин = 2700 с), и assert, что `_engine_verify_job`
не обёрнут ни в один bounded-wait (`grep -c '_engine_run_arm_with_timeout'` = 2:
объявление + единственный вызов на L1472). Обе истинны сегодня — это гейт, обязанный
блокировать любой проект, врезающий ultrareview в один из этих двух вызовов.

**Обязательный формат мутации (согласие трёх проектов, §2F).** Якорь — regexp по
уникальной строке внутри тела функции; вставка по номеру строки запрещена: она попадает
на верхний уровень файла, роняет все сьюты синтаксической ошибкой и читается как «мутация
поймана», хотя поймана не та причина. Прогон — только
`LEADV2_RUN_ALL_SELECT_ONLY=1 bash tests/run-all.sh --scope changed`; полный
`tests/run-all.sh` запускать запрещено (он переставляет пять симлинков контрольной
плоскости во временный каталог и удаляет их цели). Bash-библиотеки пробовать под
`bash -c`, не под zsh.

## 4. Чего мы НЕ знаем (UNVERIFIED)

1. **Ведёт ли `claude ultrareview --json` себя неинтерактивно из-под уже работающей
   Claude Code сессии** (вложенный вызов из bash-подпроцесса движка): не ждёт ли stdin,
   нет ли billing/consent-промпта, каков rc при отказе.
   Чем проверяется: `claude ultrareview HEAD --json --timeout 2` из `bash -c` на
   некритичной ветке, с записью rc, stdout, stderr и факта блокировки на stdin.
   Почему не проверено: сессия read-only, а вызов открывает облачную сессию.
2. **Квота/бюджет ultrareview** — в какой bucket он считается и попадает ли в 5-часовое
   окно. Чем проверяется: тот же пробег, снимок квоты до и после.
3. **Существует ли асинхронная форма ultrareview** (запустить и забрать результат позже),
   без которой §1.6 закрывает тему целиком. `claude ultrareview --help` показывает только
   `--timeout`; форма «submit + poll» не документирована. Чем проверяется: пробег с
   `--timeout 1` и попытка найти идентификатор облачной сессии через `claude agents` /
   `claude logs`.
4. **Во что уже обходится always-on `SECURITY_REVIEW_ENABLED` на лид-пути** (§1.4).
   Чем проверяется: доля `review_security task=… enabled=1` на лид-вызовах против
   lane-вызовов по журналам dispatch.
5. **Расходятся ли две существующие реализации path→risk** — `_lane_writes_class`
   (`leadv2-dispatch-code.sh:7001`) и `leadv2_review_signals`. Чем проверяется: прогнать
   обе под `bash -c` на одном списке путей и сравнить вердикты попарно.
6. **Даёт ли панель независимых архитекторов выигрыш над критиком одного черновика**
   (риск признан самим П2: разнообразие идёт только от разных провайдеров на одной и той
   же подсказке). Чем проверяется: только пост-деплой — доля Heavy-задач, где судья
   выбирает не первую арму, за 2 недели.
7. **Существует ли `/ultracode` как интерактивная слэш-команда** (в CLI-help её нет).
   Чем проверяется: интерактивная сессия → листинг `/help`. Известно смежное:
   `/code-review` принимает уровень `ultra` («deep multi-agent review in the cloud»),
   то есть интерактивный вход в тот же облачный движок существует.
8. **Исполняется ли ULTRACODE-FOR-HEAVY-01 сегодня** (`leadv2.md:142` — инструкция без
   гейта и без телеметрии). Чем проверяется: grep по STATE.md закрытых Heavy-задач на
   запись размера фан-аута, которую инструкция сама требует логировать перед запуском.

## 5. Первый шаг — что делает первая линия работы

Первая линия **не строит многоагентную проверку**. Она устраняет то, из-за чего все три
проекта опровергнуты дважды подряд: условие включения не доходит до входа движков. Четыре
независимые задачи, у каждой — одна правка и один сейчас-красный тест.

**Ш1 (параллельно; блокирует всё, что касается ultrareview).** Проба §4.1 + §4.3: один

класс решения, и тема сужается до собственного фан-аута плагина.
