# SCANNER-MISSES-PS-SUBSTRING-01 — сканер живости зелёный против живого нарушителя

## Замер

Сюита `plugins/leadv2/scripts/tests/test-liveness-tristate-01.sh` слита в main 2026-09-04
(`a596a668`). Её статическая проверка T3 запрещает решать вопрос о живости шаблоном по имени
процесса. Регексп:

```python
patt = re.compile(r'pgrep\s+-f|ps\b[^\n]*\|\s*grep')
```

Она сканирует `lib/leadv2-lane-state.sh` — и **пропускает настоящего нарушителя в этом же
файле**. Операция `reconcile`, строки ~128-145:

```python
ps = subprocess.run(['ps','-axo','pid=,lstart=,command='], …).stdout.splitlines()
for line in ps:
    if worktree not in line: continue      # ← подстрочное совпадение пути
    …
    row = {'task_id': task, 'session_id': 'recovered', … }
```

Ни `pgrep -f`, ни `ps | grep` здесь нет — есть `ps -axo` и подстрочная проверка в Python.
Регексп не совпадает, T3 зелёная, нарушитель работает.

**Цена не теоретическая.** Эта строка не просто врёт в отчёте — она **создаёт записи в
реестре**. Любой процесс, чья командная строка упоминает путь рабочего дерева (grep, `git -C`,
обход деревьев другой сессией), принимается за воркера линии, и закрытая, слитая линия
воскресает строкой `session_id: recovered` с пустым набором путей записи. Такая строка
блокирует всякую линию, объявившую свои пути. Наблюдалось дважды за вечер двумя сессиями:
строка сносилась штатным API и возвращалась через 23 минуты с другим pid.

Это ровно та болезнь, которую сюита создавалась ловить, — «зелёный прогон против пути, который
в проде исполняется и врёт». Только теперь она внутри самой сюиты.

## Задача

Расширить проверку с **двух идиом** до **класса**: «решение о живости, принятое перебором
таблицы процессов с сопоставлением по тексту».

Признак нарушения — сочетание двух вещей в одной функции:
1. получение списка процессов в любой форме (`ps` с любыми флагами, `pgrep`, чтение `/proc`);
2. отбор строк по вхождению текста (`in line`, `grep`, `=~`, `case … in *…*`, `str.find`),
   а не по числовому PID из записи.

Ищи класс, а не имена. Два идиома в текущем регекспе — частные случаи; если твоя новая проверка
их не покрывает, она хуже прежней.

Помимо `lane-state.sh` и `watch-lifecycle.sh` перечисли ВСЕ найденные места по репозиторию
в отчёте — с файлом и строкой. Не правь их: цель этой линии — проверка, а находки идут в отчёт.

## Приёмка

1. **Негативный контроль на каждое изменённое требование, прогнанный.** Обязателен контроль
   именно на этот случай: вставить `ps -axo …` + `if X not in line` ВНУТРЬ тела функции в копии
   файла и показать, что сканер её ловит и называет файл:строку. Доказательство — пара
   `baseline_rc`/`mutated_rc` и красная строка, НЕ `diff_hash`.
2. **Обратная совместимость:** прежние контроли на `pgrep -f` и `ps | grep` обязаны продолжать
   кусаться. Прогони и их.
3. **Ложные срабатывания назови сам.** Если проверка краснеет на месте, которое ты считаешь
   законным, не ослабляй её молча — выпиши случай в отчёт и обоснуй исключение поимённо.
   Ослабление проверки до «ничего не находит» формально проходит и практически катастрофа.
4. **Десять прогонов подряд, не один.** Правило принято 2026-09-04 после того, как дефект в
   соседней функции проявлялся 2 раза из 13 и только под нагрузкой: сюита, зелёная пять раз,
   ничего не доказывает. Приложи все десять кодов возврата.
