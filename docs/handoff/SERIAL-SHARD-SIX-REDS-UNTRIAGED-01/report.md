## 1. `product-close waits for worker exit` — родилась красной (`eb6f61c6`)

Случай FP-08a коммитит дифф воркера (`work_mode 2`) и требует, чтобы закрытие его увидело. Его
проходящий близнец `case_committed_worker_diff` перед этим сеет `refs/remotes/origin/main` — иначе
коммит уже сдвинул HEAD и мерить не от чего. Во freepool-случае этих двух строк нет, поэтому
закрытие честно отвечало `bytes=0 → terminal=no_work`, а четыре утверждения не могли пройти
конструктивно.

**Не регресс, а рождение красной:** прогон сюиты на вводящем коммите `e26edc67` даёт те же 54/4.
Она написана в wip/recovery-коммите и не проходила ни разу. **Связи с живым отказом `d209d246`
нет** — там двухчасовой висяк без журнала, здесь пустая дифф-база.

Контроль сделан прогоном: замена `update-ref` на равный по стоимости no-op возвращает 54/4 —
работает ссылка, а не лишние миллисекунды. В сам случай вписано предупреждение: у базы **три
независимых читателя** (`_pc_lane_commits_ahead:1543`, `_pc_diff_base:2337`,
`_pc_diff_base_main:2358`), и отключение любого ОДНОГО оставляет случай зелёным — я проверила все
три. Одноточечная мутация против избыточных читателей контролем не является.

## 2. `burn governor` — тест держал число, которое живёт в конфиге

Случай 22 утверждал литеральное `hard=90`. Губернатор читает потолок из
`config/leadv2-quota-ceilings.sh` (`leadv2-burn-governor.sh:194-198`), а там у codex сегодня **95**:
`leadv2_quota_ceiling codex build` → `95`. Вердикт продукта был правильным
(`verdict=hard reason=over_hard hard=95`), красным был тест.

Теперь случай **выводит потолок из того же источника** и толкает `used_pct` за него, то есть
проверяет «за жёстким порогом», а не конкретное число. 35/0.

Контроль: мутация **внутри ветки вердикта** (`reason=over_hard` → `over_soft`,
`leadv2-burn-governor.sh:236`) красит случаи 22, 27 и 28. Первый заход мутации не наложился —
python упал на кавычках, и прогон «контроля» прошёл по НЕмутированному файлу, показав `rc=0`.
Ассерт это поймал; без него это был бы зелёный контроль над неприменённой мутацией — третий раз за
день одна и та же форма.

### C6b, C6c — «диспетчер перестал журналить» читалось с файла, которого сюита не открывала

Журнал не живёт в `<repo>/docs/leadv2/tasks` с тех пор, как control-plane стал worktree-инвариантным:
`leadv2-journal.sh` резолвит путь через `leadv2-state-path.sh`. Измерено:

```
$ find <fixture-home> -name journal.md
.../tmp/rog1-state/tasks/dispatch-cd2e58c7/journal.md      <- сюда пишет продукт
$ grep -o 'lane_deliverable .*' .../dispatch-cd2e58c7/journal.md
lane_deliverable task=cd2e58c7 status=ignored reason=unknown_kind
```

То есть продукт писал **ровно то, что случай утверждает**, всё это время. Половина починки уже
лежала в сюите (она пиннит `LEADV2_STATE_ROOT`, чтобы не гадить в шину флота, строка ~87) — а
**читатель** на другом конце так и остался на до-миграционном пути и находил пустоту.

Правка: `run_dispatch` пиннит state-root **внутрь фикстуры**, `journal_of` ищет по всей фикстуре и
**предпочитает `dispatch-<sig8>/journal.md`**. Второе не косметика: control-plane пишет три журнала
на диспатч (`dispatch-<sig8>/`, `<sig8>/`, D1-lane-state), и первая версия этой же правки —
`-name journal.md -print -quit` — брала первый попавшийся, читала пустой ответ с чужого файла, и
C6b/C6c остались красными **по второй, другой причине**. Записано в комментарии на месте.

Парный контроль: мутация в продукте (`emit decision "lane_deliverable … reason=unknown_kind"` теряет
`reason=`) → **C6b красный (rc=1)**; на честном дереве **C6b/C6c зелёные (rc=0)**. Случай по-прежнему
проверяет, а не находит.

### C4 — золотой эталон, приколоченный к рефу 78 коммитов назад

Живой и pre-gate прогон расходятся **ровно в одном поле**:

```
live=[... diff: 1cce5a84 ...]   pre=[... diff: 9473d886 ...]
status / reviewer / findings_source / findings / report — совпадают побайтно
```

`diff:` — хеш **содержимого** отскопленного диффа, и правила скоупинга сами по себе движущаяся
мишень: с `PRE_GATE_REF` (`1806b4f4`) файл `leadv2-dispatch-product-close.sh` изменён **78 раз**, и
часть этих изменений — намеренные правки скоупа (orchestration dirt, bootstrap dirt, index-blind).
Два живых прогона дают один и тот же хеш, то есть он детерминирован — просто не инвариантен к
осмысленной работе над скоупом.

Правка: сравнение полей решения без `diff:`, плюс **сохранённое** требование, чтобы хеш был на
обеих сторонах и имел форму 8 hex.

**Цена названа, а не спрятана:** эталон больше не замечает изменения в том, ЧТО попало в дифф, —
только в том, что гейт РЕШИЛ. Обе оставшиеся половины живые, проверено мутациями:
`reviewer: mutated-%s` → **C4 красный**; пустой `diff:` → **C4 красный**
(`golden mismatch (diff hash shape): live=[] pre=[9473d886]`); честное дерево → **C4 зелёный**.

### Побочная находка (наша, не продукта)

Перезапись файла сюиты, пока предыдущий её прогон ещё исполняется, ломает тот прогон на середине
(bash дочитывает скрипт по мере исполнения) — в логе это выглядит как синтаксическая ошибка на
строке из второй половины файла. Первый «после-правочный» прогон был испорчен именно так; вердикт
взят с чистого повторного прогона.
