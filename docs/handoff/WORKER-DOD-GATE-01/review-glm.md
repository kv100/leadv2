## Обоснование двух высоких находок

**High 1 — Проверка (d) структурно инертна на пути подключения.** Шлюз подключен в `leadv2-dispatch-product-close.sh:2750-2797` и считывает `${diff_file}`, который является `${HANDOFF}/review.diff` (единственное присваивание, `leadv2-dispatch-product-close.sh:1933`, выполняемое вызовом `pc_scope_diff` на 2564 — порядок корректен). Но каждый вызов, который создает review.diff, исключает именно пути состояния времени выполнения:

```
$ sed -n '1932,2145p' .../leadv2-dispatch-product-close.sh | grep -n 'exclude'
56:  gitdir="$(git -C "${repo}" rev-parse ... || { git -C "${repo}" diff "${base}" -- "$@" ':(exclude)docs/leadv2' ':(exclude)docs/handoff' ...

```

Против `_DOD_RUNTIME_STATE_REGEX='^(docs/leadv2/|docs/LEAD_V2_STATE\.md$|docs/handoff/dispatch-nw)'` (`lib/leadv2-dod-gate.sh:27`), два из трех семейств путей (`docs/leadv2/*`, `docs/handoff/dispatch-nw*` — те самые файлы, которые мотивировали эту задачу) на этом пути могут появляться только через `+++ b/` из *рабочего дерева*, что никогда не происходит. Выживает только `docs/LEAD_V2_STATE.md`. Тест подключения передает синтетический diff, поэтому тест никогда не замечает этого. Весь рабочий `git-diff` существует в `lv2_dod_retry_or_finalize()` — который в отчете указан как не подключенный ни к одному из 4 wrappers. Итог: заголовок «ваш diff не должен затрагивать пути состояния времени выполнения» не соблюдается на пути, где заявлено, что шлюз работает.

**High 2 — Привязка `diff_hash` несовместима между производителем и потребителем.** На рабочем пути шлюз хэширует любой `diff_file`, который ему передали (строка 219: `diff_hash="$(_dod_sha256 "${diff_file}")"`), а на подключенном пути это review.diff — агрегат между репозиториями, разрешенный по pc's base-ref, с исключениями путей. Воркер запускает `leadv2-mutation-control.sh` во время сборки, когда review.diff еще не существует; README инструмента говорит, что воркер вычисляет его «по тому же шаблону, что и `_review_diff_hash()`», который хэширует DIFF_FILE (проверено: `leadv2-review-run.sh:597-611` — это `shasum -a 256 "${DIFF_FILE}"`). Собственный рабочий прогон автора привязал `a088af…` к `git diff main HEAD -- plugins/leadv2/scripts tests/run-all.sh` (раздел «Этот шлюз против собственного diff задачи» в report.md) — другая область пути, другая база, другие исключения, чем в review.diff. Этот хэш никогда не может совпадать с sha256(review.diff), поэтому любой бриф, содержащий строку вставки «mutation-control», получает `dod_fail check=mutation_control_not_via_runner` → exit 7 при *отказе после соблюдения требований*. ## Низкие находки

- **L1** `test-worker-dod-gate.sh:401` — `LEADV2_TARGET_ROOT_OVERRIDE=1` — это no-op: grep подтверждает, что эта переменная не существует нигде в `leadv2-mutation-control.sh`. Вводящий в заблуждение мертвый ключ, предполагающий семантику переопределения.
- **L2** `_dod_diff_paths` (`lib/leadv2-dod-gate.sh:100-104`) соответствует `^--- a/` / `^+++ b/` в столбце 0, который также может быть строкой *удаленного содержимого*, буквальная полезная нагрузка которой начинается с `-- a/...` (маркер удаления + содержимое). Ложное срабатывание → ложный сбой проверки (d) / фантомный путь в переписи проверки (c). Консервативно, но реально для коммитов, удаляющих встроенный diff-текст.
- **L3** Подключение выполнено с ошибкой fail-open: rc=3 шлюза явно проходит как pass, а пустой `FOUNDER_TASK_ID` или отсутствующий файл шлюза пропускает шлюз полностью без примечания — что противоречит собственной доктрине «никогда не быть тихим проходом» для собственных режимов сбоя шлюза (rc=2 обрабатывается правильно).
- **L4** `leadv2-review-run.sh` defense-in-depth: путь rc=1 вызывает `_review_state_write`, путь rc=2 (строки ~1349-1358) — нет. Несогласованная запись состояния для заблокированного случая.
- **L5** Sed-режим `leadv2-mutation-control.sh` (§4) не может обеспечить «применяется ровно один раз» — anchor_count обнаруживает только no-op; многострочное совпадение sed проходит без учета количества. Честно признали в комментарии, но код выхода/артефакт все равно утверждает `anchor=<sed>`.
- **L6** `lv2_dod_retry_or_finalize` (worker-epilogue.sh:208-252): счетчик `.dod-attempt` никогда не сбрасывается между раундами, а также `_dod_check_b` возвращается к `${task_dir}/.dod_*.tmp`, когда `mktemp` завершается с ошибкой, записывая временные файлы в зафиксированный каталог задач. Сегодня это спорно (нулевое количество вызовов, как признает отчет), но обе формы останутся, когда он будет подключен.
