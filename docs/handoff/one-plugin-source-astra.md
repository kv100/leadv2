## Decision and strongest findings

Choose **a declared, small, machine-checked project layer**. The only editable source of generic orchestration is the tracked `plugins/leadv2/` tree in the plugin repository. Projects retain application adapters, domain-specific agents/hooks, and typed project policy. Legacy plugin entry paths may remain generated symlinks, but never independently editable implementations. Installed runtime trees are delivery artifacts, with source revision and content verification, never development locations.

The framing “projects have different copies of the plugin” misses the main remaining problem. The census below verifies the absence of top-level real script collisions in persona-engine and Getmany, and the Respiro `codex-guard.sh` collision. It also finds drifted Getmany agent definitions and extensive untracked shadow code in leadv2 itself. **Absence of a same-name canonical file does not establish that a script is application-native**: old `leadv2-*`, retired wrappers, tests, backups, and generated bytecode need separate treatment.

The mechanism actively recreates copies. `plugins/leadv2/scripts/leadv2-plugin-sync.sh:885-898` rsyncs shared scripts/contracts/hooks; `:1003-1023` rsyncs the plugin repository's own `.claude/scripts`. Those writers must change before conversion. Merely linking files and tightening prose would be undone by the next sync. Existing direction-safety comments even describe proceeding after unavailable quarantine; the proposed migration must instead refuse any write without a verified preimage.

Do not delete overrides wholesale. The file ledger identifies meaningful application integrations, contradictory policy, unused keys, tests, fixtures, and mutable state mixed into this directory. “Not observed executing” is not proof of dead code. Unknown cases are retained until their named removal proof succeeds.

The separate P0 `GATE-RUNS-AN-UNTRACKED-HALF-SIZED-CORE-RUNNER-01` has a stale routing premise at this snapshot: both main and the lane already prefer the tracked runner. The old untracked runner remains. This report neither fixes nor administratively closes that P0. The compatible end state is a tracked runner selected directly by the plugin's own test wrapper, with no dependence on the compatibility directory.

## Exact end state and ownership boundary

The source namespace is `plugins/leadv2/{scripts,hooks,agents,commands,skills,contracts,config,...}`. Add a tracked plugin-owned manifest generated from `git ls-files -s plugins/leadv2`, with public entry IDs and extension-point schemas. Internal helpers use physical plugin-root resolution; project data uses a separate, explicit project root. A plugin lane tests its own tracked plugin tree. An application lane runs the admitted runtime revision and its own application checkout. Neither may infer the other root from an ambiguous `../..` walk.

Each application owns a proposed `.leadv2/project.yaml` and application files under a declared namespace such as `tools/leadv2-project/`. The manifest declares project ID, schema version, required plugin API version, typed config deviations, and exact adapter/agent/hook paths with capabilities and test entrypoints. Runtime state moves to the existing configured control-plane state root, fixtures to project tests, and historical material to a non-discovered archive. No `.state`, test fixture, or archive file is a configuration override.

Example schema shape (proposed, not installed):

```yaml
schema: 1
project_id: respiro-ios
plugin_api: 1
policy:
  codex_enabled: true
  paths:
    tasks: null  # explicit disable; omission is different
extensions:
  deploy:
    path: tools/leadv2-project/deploy.sh
    capability: application-deploy
    test: tests/leadv2-project/deploy-contract.sh
  agents:
    swift_developer: .claude/agents/02-swift-developer.md
```

The normal authoring rule is mechanically decidable: files under the plugin namespace are plugin-owned; files under the project namespace must be named by the project manifest; compatibility paths must match the generated link manifest; undeclared executable/configuration entries fail admission. No override can introduce arbitrary resolver precedence or replace a plugin entry ID. Reserved plugin basenames cannot be registered as project adapters. A new project hook must declare its event and capability, and cannot shadow a plugin hook or generic routing/approval gate. Project policies may tighten safety constraints; conflicts with mandatory plugin gates fail schema validation rather than “last prose wins.”

Hash comparison catches a renamed byte-identical plugin copy; provenance records catch known retired entries after upstream deletion. A machine cannot reliably recognize arbitrary rewritten semantic clones. The enforceable invariant is therefore **closed registration and immutable ownership**, not “an AI decides whether a new script feels generic.” Registering a new project extension is an explicit typed API change reviewed with its test and rationale. Once registered, every edit is classified without human adjudication. Existing orphan `leadv2-*` files are quarantined from automatic conversion until their ancestry/consumers are accounted for.

`.claude/scripts/` in the plugin repository becomes a generated compatibility link farm into its **own checkout's** `plugins/leadv2/scripts/`, including required subdirectories. Retain only links needed by known callers; real native tooling moves to the declared project namespace. Do not replace the whole mixed directory by a symlink. Worktree-relative targets must resolve into that lane, not main. The P0 runner must continue using its tracked path directly. New files appear through manifest regeneration, not recursive copy sync. Deleted upstream entries are found by a reverse destination scan as well as a source scan, so dangling/orphan links cannot evade the check.

In applications, generated legacy links resolve through the admitted plugin runtime root. Projects need not link every internal plugin file: expose only required compatibility entries. Global shared scripts can become a directory alias only after the full subtree is proved plugin-owned and no native payload remains; until then use individually declared links. The same rule applies to shared hooks/contracts and user-global leadv2 entries. Do not replace all of `~/.claude`, shared state, or user scripts.

Installed/cache artifacts require exact source SHA, manifest digest, and no local edits. They may be generated immutable delivery snapshots if the host requires materialized files. They are not another source to merge back automatically. **UNVERIFIED: host acceptance of symlinked plugin installations and dynamic path rebinding was not tested; an isolated host install/start/reload probe with resolved-path output is a prerequisite to choosing its transport.** The design does not depend on undocumented host symlink semantics. Local source linkage remains the authoring authority; admission controls prevent live lanes reading a changing source revision.

Why not “every project file is a symlink”? It erases application adapters and domain policy, makes project-local edits write through into the shared source, and does not prevent drift elsewhere. Why not “projects hold nothing, use only `~/.claude/plugins`”? The observed deploy/verify/status extension contracts need project behavior and policy. Moving them into the plugin hardcodes application knowledge centrally; relying on a cache path merely moves the ambiguity to an unversioned installation. The chosen layer makes the remaining variation explicit and testable.
