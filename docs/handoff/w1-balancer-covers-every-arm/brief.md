## Правило, обязательное к соблюдению
**Переиспользовать существующее.** `leadv2-claude-profile-pick.py` — зрелый рабочий скорер:
он уже считает по каждому аккаунту СВЯЗЫВАЮЩЕЕ окно (`usable_now = remaining_pct /
hours_to_reset`), различает `five_hour` и `seven_day` и намеренно НЕ схлопывает их в `max()`.
Его расширяем. **Второй балансировщик писать запрещено.** В отчёте назвать словами, какой
именно существующий компонент расширен и в каком месте.

## 1.1 — балансируется одна рука из всех
Наш собственный комментарий, `leadv2-dispatch-code.sh:7865-7875`:
«The balancer is not broken (measured: it correctly follows lower utilisation)» и
«Threaded only into the sonnet arm … ignored, WARN-only, on every other arm».
Подтверждено двумя независимыми чтениями: `claude-subsession.sh:495` — единственный вызов
`leadv2-claude-profile-select.sh`; `leadv2-dispatch-code.sh:60` — `arm=sonnet -> claude-subsession.sh`.
Значит **fable, opus и haiku не балансируются вообще**.

Сделать: провести через селектор профилей КАЖДУЮ руку Claude, а не только sonnet. Там, где
рука запускается не через `claude-subsession.sh`, — назвать этот путь в отчёте и провести
выбор профиля по нему же, а не оставить `WARN-only`.

## 1.3 — селектор не понижает профиль самого лида
`leadv2-claude-profile-select.sh:116-117`: «no manual list, no hardcoded profile exclusion».
Ничто не мешает диспатчеой руке сесть на тот аккаунт, который лид уже жжёт; расход лида
попадает в пробу с запаздыванием, поэтому окно выглядит свободнее, чем оно есть.

Сделать: определить профиль ТЕКУЩЕЙ сессии (у селектора уже есть
`LEADV2_CLAUDE_PROFILE_DEFAULT_DIR`) и ставить его **последним** в ранжировании.
**Понижать, а не исключать** — при единственном живом аккаунте работа обязана продолжаться.
Плюс журналировать выбранный профиль в строке диспатча: без этой строки совпадение с окном
лида остаётся неизмеримым.

## Приёмка — обязательный негативный контроль, проверяется лидом
1. Сюита: для КАЖДОЙ руки Claude доказать, что выбор профиля произошёл (строка в журнале
   с именем профиля), а не был пропущен как `WARN-only`.
2. Сюита: при двух живых аккаунтах, где один — профиль текущей сессии, выбран должен быть
   ДРУГОЙ; при одном живом — работа не встаёт.
3. Негативный контроль: вернуть `WARN-only` для одной руки и убрать понижение профиля лида —
   мутацию вставить ВНУТРЬ тела функции, не на верхний уровень файла. Сюита обязана покраснеть
   на конкретном названном тесте.
4. В отчёт вставить зелёный и красный прогон целиком, плюс артефакт мутации в
   `docs/handoff/w1-balancer-covers-every-arm/mutation-control/`. Лид прогоняет мутацию
   независимо на НАСТОЯЩЕМ файле; сюита, мутирующая только свою копию, доказательством не
   считается.
