### ПОПРАВКА-2: класс — «читатель предполагает одну строку», и таков же сам дедупликатор

Переформулировка сессии fb, принята 2026-09-04, и она сильнее прежней. Класс дефекта — не
«словарь по `task_id`», а **«код предполагает одну строку на задачу»**, в двух формах:

- **словарь** `{task_id: row}` — побеждает ПОСЛЕДНЯЯ строка (6 боевых мест);
- **`next((s for s in sessions if s.get("task_id") == task_id), None)`** — побеждает ПЕРВАЯ
  (десять мест в четырёх файлах: `leadv2-active-registry.sh` (девять), `lib/leadv2-lane-state.sh`,
  `leadv2-fanout-lane-launcher.sh`, `leadv2-provider-canary.sh`, `leadv2-phase8-close.sh`).

Отсюда главный симптом, которого не объясняла прежняя формулировка: **писатель и читатель на
дублированной линии работают с РАЗНЫМИ записями и оба уверены, что запись одна.** Регистрация
правит первую строку, живость и статусная строка читают последнюю. У D3 три строки: первая
несёт настоящий указатель, последняя — `None`.

**Найден писатель (`leadv2-active-registry.sh:420-441`), и он же — дедупликатор:**

```python
existing = next((s for s in sessions if s.get("task_id") == task_id), None)
if existing:
    if _pid_alive(existing.get("pid")):  refresh_existing = True; ...
    else:                                sessions.remove(existing)   # снимает ОДНУ
if not refresh_existing:                 sessions.append({...})
```

Логика написана правильно для одной строки и не может сойтись при двух: `next()` осматривает
только первую, `remove` снимает только её, затем добавляется новая — в конец. Средние строки
не осматриваются никогда. **Механизм, обязанный предотвращать дубли, сам написан в допущении,
что дублей нет**, поэтому после появления второй строки он не сходится ни при каком числе
попыток: вечно снимает первую и дописывает последнюю.

Смыкается с `SD-REGISTRY-PID-ONE-IS-IMMORTAL-01`: при `pid: 1` ветка `_pid_alive` всегда
истинна, значит строка вечно «обновляется» вместо замены и живёт бесконечно.

- **GO-условие (заменяет прежнее):** на линии с ТРЕМЯ строками писатель и читатель сходятся
  на одной и той же записи; проверяется живой пробой по D3, ожидается `finished_unlanded`.
- **Действие:** осматривать ВСЕ строки задачи, не первую и не последнюю.
- **Открыто:** комментарий `# last-write-wins on dup task_id` в `lanes-snapshot.sh:644`
  говорит, что дубли считались нормой — значит существует и писатель, плодящий их намеренно.
  Найден один (регистрация, ненамеренно); намеренного пока нет.

### SD-PHASE-GATE-ACCEPTS-ATTESTATION-AS-PROOF-01 — фазовый гейт доказывает бумагу, а не фазу

Замер 2026-09-04 по всем 999 записям фаз на диске:

|---|---|
| поля нет вовсе | **453** (45%) |

Как это выглядит на живой линии: диспатч отказывает с `missing mandatory phases: plan,gate1`,

делала ровно то же весь вечер во ВСЕХ своих диспатчах. **Отказ снимается не тем, что фаза
случилась, а тем, что появился файл с нужным именем.**

Это та же болезнь, что аллоулист `.gitignore` (разрешение по ИМЕНИ файла) и подсчёт «слито»
по теме коммита: бумага, читаемая как работа. Третье её появление за вечер.

- **Due:** ближайшая свободная линия волны В4.
- **GO-условие:** дважды. (1) запись с `proof: attested` или без поля НЕ снимает обязательную
  фазу — диспатч по-прежнему отказывает; (2) запись с нулевой длительностью отвергается.

### SD-REGISTRY-IS-TRACKED-BY-GIT-SO-EVERY-WORKTREE-HAS-ITS-OWN-01 — корень ночной путаницы

Найдено сессией fb, подтверждено и расширено ведущей 2026-09-04. Это КОРЕНЬ; предыдущие строки
про реестр — его следствия.

**`docs/leadv2/active.yaml` отслеживается гитом** (`git ls-files` подтверждает). Каждое рабочее
дерево линии получает СВОЮ копию, замороженную на коммите ветки. Процесс внутри дерева читает
копию своего дерева. Замер — ЧЕТЫРНАДЦАТЬ копий, от 5 до 106 строк: пять деревьев несут по 106,
главная копия 9, общая 5, плюс `.ephemeral/repo` (74) и `repo2` (19) и вложенные формы пути.

**Объясняет разом всё, что мы весь вечер объясняли по отдельности:**
чистка 106 → 12 сработала в главной копии, в деревьях осталось 106 призраков;
`leadv2_active_unregister` возвращает rc=0 и не меняет ничего у читателя (fb: 6 вызовов, было 9
строк, стало 9); `writeset_conflict` против строк, которых в главной копии нет; рендер печатает
«5 sessions» при 9 строках; «два реестра расходятся» — частный случай, их не два.

**Доктрина:** живое состояние не имеет права быть отслеживаемым файлом. Git раздаёт копии по
деревьям по построению, а дерево линии — снимок прошлого. Реестр живых линий в git гарантированно
показывает каждому читателю разное прошлое.

- **Due:** сразу после `SD-E2E-GATE-BROKE-TODAY-…`; блокирует всякую работу с линиями.
- **GO:** `find` по всем деревьям находит РОВНО ОДИН `active.yaml`, вне индекса git; снятие
  регистрации из любого дерева меняет именно его.
- **Действие:** вынести живое состояние из репозитория, разрешать путь абсолютно.
- **Rollback:** вернуть в индекс — вместе со всеми следствиями выше.

## SD-PENDING-WINDOW-REFUSES-EVERY-HONEST-DECLARER-01 — объявил набор записи честно — получил отказ
- **Due:** сразу. Пока не починено, все три сессии ходят с `LEADV2_WRITESET_PENDING_WINDOW_SEC=0`.
- **GO:** диспатч с непустым `--writes` при живой чужой строке моложе 900 с проходит, а диспатч
  с НАСТОЯЩИМ пересечением путей по-прежнему отвергается кодом 5. Обе пробы в одном прогоне.
- **Action:** снять замыкание в паре «двухфазная регистрация + `_lv2_ws_pending`»: либо первая
  регистрация обязана нести уже разрешённый набор, либо окно pending обязано сравнивать пути,

- **Why:** замер 2026-09-04T01:33Z, воспроизведён напрямую со stderr, который диспетчер глушит
  через `2>/dev/null`: `[registry] writeset conflict: other=D2-E4-… reason=pending_resolution`,

  Замыкание: диспетчер регистрирует строку РАНЬШЕ, чем разрешает её набор (вторая фаза правит
  строку после прохода архитектора), поэтому у живой строки `writes: null` по построению. При

  два: `writes: null` при `enforce=block` и e2e-гейт, гоняющий весь набор для линии с одним
  файлом). Линия, не объявившая ничего, проходит; объявившая честно — нет.

  объявила их призраками. Они были восьмиминутными строками нашей же волны перезапуска.
