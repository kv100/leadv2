# Suites that are red on `main` and tolerated so an unrelated lane isn't
# blocked by a suite it never touched (measured via `tests/run-all.sh
# --scope changed`, which always runs the full curated
# plugins/leadv2/scripts/tests/run-core-offline.sh set regardless of scope).
# Fixing them is out of scope here — that is FIFTEEN-RED-SUITES-01 /
# SD-MAIN-CORE-SUITE-RED-01 (by-name tracking: docs/leadv2/scheduled-decisions.md),
# separate tasks. This file exists so the CI job (and every lane's e2e gate,
# leadv2-phase8-e2e-gate.sh) can be green without hiding NEW regressions:
# tests/ci-gate.sh and the run-core-offline.sh wrapper classification in
# tests/run-all.sh both treat a failing suite on this list as a known issue
# (reported, non-blocking) and any failing suite NOT on this list as a hard,
# blocking failure — for EVERY lane, because run-core-offline.sh is one
# wrapper suite classified all-or-nothing (every failing nested suite must be
# allow-listed for the wrapper to read as non-blocking). One unregistered red
# here fails every lane's gate, not just the lane that caused it — that
# amplifier is exactly what let this list rot silently 2026-09-02 -> 09-14:
# 13 suites went red after the snapshot and nobody could cheaply notice.
#
# Format: one entry per line, `core:<exact [CORE-OFFLINE] FAILED: label>` for
# suites that run nested inside run-core-offline.sh, or `path:<repo-relative
# suite path>` for a suite that fails at the top level of tests/run-all.sh. A
# trailing `# <script path> — <reason>, dated YYYY-MM-DD` comment is REQUIRED
# so a reader never has to reproduce the failure locally just to find out
# what it is, and so tests/known-red-guard.sh can verify freshness.
#
# GROWTH RULE (revised 2026-09-14 — the old "may only shrink, no exceptions"
# rule is what caused the rot: it gave no legitimate channel to register a
# suite that went red after the baseline snapshot, so genuinely new reds were
# never added and instead silently blew the blast radius of every lane's
# gate). The list may still only shrink for FREE — removing an entry never
# needs justification — but it may GROW when, and only when, the new entry
# carries a dated reason comment (a `YYYY-MM-DD` token). tests/known-red-
# guard.sh enforces the date-token requirement on every entry and additionally
# refuses (a) an entry whose label does not match any current SUITE_DEFS
# label in plugins/leadv2/scripts/tests/run-core-offline.sh (a stale/renamed/
# removed entry — rot in the other direction) and (c), when invoked with a
# transcript-file argument, an entry that is demonstrably passing in that
# transcript (the GONE-GREEN case tests/run-all.sh already detects and prints
# informationally without failing; tests/known-red-guard.sh's check 4 makes
# the same signal a hard refusal when a transcript is supplied).
#
# B2-GATE-BUDGET-4 (2026-09-09): under --scope changed / changed-since (the
# close gate and PR CI — the BUDGET paths), tests/run-all.sh asks
# run-core-offline.sh to SKIP these suites entirely
# (LEADV2_CORE_OFFLINE_SKIP_KNOWN_RED=1; skipped labels are relayed as
# [KNOWN-RED-SKIP] lines). They are still EXECUTED by --scope all (the
# nightly full sweep) and by a bare run-core-offline.sh invocation, and a
# `core:` label that PASSES a full-set run is surfaced by run-all as
# [KNOWN-RED-GONE-GREEN] — that is the signal to remove the entry here: the
# skip would otherwise hide a suite that quietly went green, and the list
# would become permanent.
